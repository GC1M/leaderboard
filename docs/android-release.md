# Android builds and releases

Package id: `com.shivamlalakiya.leaderboard` (set in `app.config.ts`, same as the iOS bundle id). `android/` is generated by `npx expo prebuild` (Continuous Native Generation) and is gitignored, so every build starts from `app.config.ts` plus config plugins. Never edit or commit `android/`.

Builds need JDK 17 (what React Native 0.88 compiles with) and the Android SDK for local Gradle builds, or an Expo account for EAS builds. EAS CLI is not a dependency; run it with `npx eas-cli@latest` or a global install.

## Build profiles (`eas.json`)

| Profile | Output | Distribution | Use |
| --- | --- | --- | --- |
| `development` | Debug APK (`:app:assembleDebug`) | internal | Developers. Loads JS from Metro (`npm start`), so the phone must reach your machine |
| `preview` | Release APK, JS bundled | internal (EAS install link) | Testers sideloading outside Play |
| `production` | Release AAB | Play Console | Play internal testing track and later releases |

`development` is a plain debug build, the same thing `npx expo run:android` produces. It does not use `developmentClient` because `expo-dev-client` is not installed; add it (`npx expo install expo-dev-client`) and set `"developmentClient": true` if you want the dev launcher.

Each profile sets `environment` (`development`, `preview`, `production`), which selects that EAS environment's variables at build time. Nothing is committed. Set these per environment on expo.dev (Project, Environment variables) or with `eas env:create`:

| Name | Visibility |
| --- | --- |
| `EXPO_PUBLIC_SUPABASE_URL` | plain text (it ships in the app) |
| `EXPO_PUBLIC_SUPABASE_ANON_KEY` | plain text (it ships in the app) |
| `EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID` | plain text |
| `EAS_PROJECT_ID` | plain text |

`EXPO_PUBLIC_*` values are compiled into the JS bundle, so they are not secrets, but keep them out of git anyway. A build without the Supabase pair starts but cannot sign in.

## First EAS setup (needs an Expo account, owner only)

1. `npx eas-cli@latest login`.
2. `npx eas-cli@latest init`. It creates the project on expo.dev and prints the project id. It cannot write it into `app.config.ts` (a dynamic config); that is intended. Export it instead: `export EAS_PROJECT_ID=<id>` in your shell or `.env`, and add it as an EAS variable in every environment. `app.config.ts` only adds `extra.eas.projectId` when the variable is set.
3. Add the variables above.
4. `npx eas-cli@latest build -p android --profile preview`. On the first release build EAS offers to generate the upload keystore; accept (see Signing).

## Tester APK

Two ways:

- EAS: `npx eas-cli@latest build -p android --profile preview`. The build page has an install link and QR code; send it to testers. This build has the JS bundled and real Supabase env, so it works on its own.
- CI: every CI run uploads `android-debug-apk` (Actions, the run, Artifacts; kept 7 days; arm64 only). It is a debug build with a dummy Supabase URL that loads JS from Metro, so it is for developers checking a native change, not for testers.

Tester install (sideload):

1. Open the install link (or copy the APK) on the Android phone.
2. Allow the browser or Files app to install unknown apps when Android asks (Settings, Apps, Special app access, Install unknown apps).
3. Install, open, sign in.
4. If the phone has an older build signed with a different key (debug vs release), uninstall it first; Android refuses the update otherwise.

Through Play instead (needs the Play Console): upload a `production` AAB to the internal testing track, add tester emails or a Google Group, and share the opt-in link. Testers install from the Play Store, no unknown sources needed. Health Connect permissions only work fully for Play-distributed builds once the declaration below is approved.

## Signing

No keystore, password or `credentials.json` is ever committed (`.gitignore` covers `*.keystore`, `*.jks`, `credentials.json`, `google-services.json`, `android/`; the CI gitleaks scan backs it up).

- Debug builds (local, CI, `development`) use the Android default debug keystore (`~/.android/debug.keystore`, generated by the SDK, password `android`). Each machine has its own, so debug builds from different machines cannot update each other.
- Release builds (`preview`, `production`) are signed with the upload key. Recommended: let EAS generate and store it (`eas credentials`, Android, the profile, Keystore). Download a backup from there and keep it in a password manager. Local release signing is not set up: the generated `android/` signs `release` with the debug key. If it is ever needed, keep the keystore outside the repo and feed it through `~/.gradle/gradle.properties` with a config plugin, never through a committed file.
- Play App Signing: Google holds the app signing key that signs what users install from Play. You upload AABs signed with the upload key; if the upload key is lost, Play support can reset it, the app signing key is never at risk.

### SHA-1 fingerprints

Google sign-in needs an Android OAuth client per signing certificate (package `com.shivamlalakiya.leaderboard` plus SHA-1) in the Google Cloud project. Register each one that signs builds you use:

| Certificate | Signs | How to get the SHA-1 |
| --- | --- | --- |
| Debug | local and CI debug builds | `keytool -list -v -keystore ~/.android/debug.keystore -alias androiddebugkey -storepass android` (per machine), or `cd android && ./gradlew signingReport` |
| Upload | `preview` APKs, `production` AABs | `npx eas-cli@latest credentials`, Android, pick the profile; or Play Console, Test and release, App integrity, App signing, Upload key certificate |
| Play app signing | anything installed from Play | Play Console, Test and release, App integrity, App signing, App signing key certificate |

## Versioning

`version` in `app.config.ts` (`1.0.0`) is the user-visible version name; bump it by hand for a release. `versionCode` is managed remotely: `eas.json` sets `"appVersionSource": "remote"` and the `production` profile has `"autoIncrement": true`, so EAS stores the last versionCode and adds one on every production build. Nothing has to be committed per build and two people building cannot collide. `preview` and `development` reuse the current remote value without bumping. Local and CI builds use `versionCode 1` (no value in `app.config.ts`), which is fine because they are never uploaded to Play.

If Play already has builds when EAS is first linked, set the starting point with `npx eas-cli@latest build:version:set -p android` to the highest versionCode Play has seen.

## CI

The `android` job in `.github/workflows/ci.yml` runs on every PR: JDK 17 (Temurin), `npm ci`, `npx expo prebuild --platform android --no-install`, then `./gradlew :app:assembleDebug -PreactNativeArchitectures=arm64-v8a` with Gradle caching (`gradle/actions/setup-gradle`). It is the only place Android native code (local Expo modules in `modules/*/android`, native dependencies, config plugin output) is compiled, so a Kotlin or plugin break fails here. It uploads the debug APK. The `check` job also bundles the Android JS (`expo export --platform android`). Both feed `ci-ok`. See [ci.md](ci.md).

Reproduce locally (JDK 17 and Android SDK installed, `ANDROID_HOME` set):

```bash
npx expo prebuild --platform android --no-install
cd android && ./gradlew :app:assembleDebug -PreactNativeArchitectures=arm64-v8a
```

Prebuild also rewrites the `android` and `ios` scripts in `package.json`; do not commit that change.

## Health Connect declaration

Play requires a Health Connect permissions declaration (Play Console, App content, Health apps) for every health permission the app requests, plus a privacy policy, before a build with those permissions can be released on any track. See [play-console-health-connect.md](play-console-health-connect.md). What the app reads and which capabilities Android does not support are in [android-health-capabilities.md](android-health-capabilities.md).
